# Dependency upgrades

Preserve the immutable supply-chain reference and a tested rollback. An upgrade
is not safe merely because it is patch-sized or generated by Renovate.

## Sources of truth

Read before changing a pin:

- [Renovate policy](../../renovate.json)
- [Service modification and rollback](../../docs/service-operations.md#modify-a-service)
- [Cluster and node lifecycle](../../docs/cluster-operations.md)
- [Operational runbook](../../docs/runbook.md)
- [Cluster validation workflow](../../.github/workflows/validate-cluster.yml)
- [Flux Git pin validator](../../scripts/ci/validate-git-source-pins.py)
- [Immutable Helm renderer](../../scripts/ci/render-helm-releases.sh)

For a service-specific dependency, also read that service's catalog descriptor,
manifests, runbook section, and the upstream release notes. Discover current
versions, tags, commits, digests, checksums, grouping, schedules, and labels from
the repository and the PR; do not reuse values from an old task description.

## Authorization boundary

- Reviewing a PR or proposing an upgrade is read-only. Do not edit, push,
  approve, merge, close, rerun workflows, publish images, or change live state
  unless the user requested that action.
- Editing a dependency pin does not authorize publishing a custom image or
  merging to `main`. A merge changes production through Flux.
- Do not trigger branch-push image workflows merely to test a build without
  acknowledging their remote registry side effect.
- Never weaken a digest, tag/commit pair, checksum, architecture requirement,
  high-risk boundary, or validation check to make an update pass.
- Stateful schema migrations, network-critical components, storage drivers,
  cluster bootstrap components, and major database upgrades require an explicit
  migration/rollback decision and, where applicable, a verified backup.

## Classify the update before editing

Inspect the complete PR diff, not only the dependency bot's summary. Classify
each changed dependency independently:

- image digest rebuild with unchanged tag
- image release change
- repository-built custom image
- Helm/OCI chart and rendered manifest change
- Flux Git source tag plus immutable commit
- Git commit or downloaded release asset plus checksum
- workflow action commit
- Flux/K3s bootstrap release, installer, manifest checksum, or controller digest
- application library or lockfile
- major, stateful, network-critical, security, or grouped update

Use `renovate.json` to understand why an update is grouped, delayed, disabled,
or labeled. Do not override disabled major/database or coupled-source rules
without a separately reviewed migration plan.

## Preflight

For every pin being changed, record:

1. Current and proposed repository, tag/version, digest/commit/checksum, and all
   consumers found with `rg`.
2. The exact upstream release or build corresponding to the proposed immutable
   reference. Verify against the primary upstream source.
3. Target architecture support for every node on which the workload can run.
   A manifest-list digest is not enough; inspect the index/platform entries.
4. Release notes, security advisories, breaking changes, removed flags, config
   migrations, schema changes, minimum Kubernetes/runtime versions, and known
   rollback limits.
5. Persistent-state implications. An old image may not read data migrated by a
   new image.
6. The previous full immutable reference and a concrete revert path.
7. For a stateful update, the exact recent completed backup and read-test.
8. For a grouped PR, whether components really form one rollout and rollback
   unit. Split unrelated risk when the task permits it.

If primary release information or architecture evidence is unavailable, report
that uncertainty and stop before merge or publication.

## Update rules

### Container images

For ordinary images, keep the complete `repository:tag@sha256:digest` form.
Never replace a digest with a mutable tag or drop a useful release tag. Preserve
intentional variants and channel constraints. For any digest-only rebuild, still
review provenance/release metadata and the
architecture list; the bytes changed even if a channel name did not.

Find every copy of a coupled image reference. Some pins intentionally appear in
more than one values field or workload and must advance together.

Verify the digest is the multi-arch image index (an OCI index or manifest list
listing every architecture the workload may run on), not a single-platform
manifest. Docker Hub tags with an `amd64-` prefix (for example the linuxserver
images) resolve to amd64-only manifests; pinning that digest breaks any pod
that can schedule to the arm64 node with `no match for platform in manifest`
(PRs #293/#297). Resolve the digest from the unprefixed version tag, then
verify the index actually lists `arm64` (and `amd64`) before committing. GHCR
`tags/list` is truncated and unsorted; do not treat its first page as the
newest version. Cross-check GHCR-published apps against the upstream GitHub
release.

Never change the pod template of an existing Kubernetes `Job` — including only
its image digest — unless the Job object is removed first. Jobs are immutable;
a digest bump on `apps/stork/bootstrap-job.yaml` (the `stork-lockdown-v1`
Job) fails Flux dry-run with `Job.batch ... is invalid: spec.template ...`
(commit 57e810e, PRs #293/#295). If an update touches an immutable Job, delete
the live Job in the same reviewed change, or leave the Job's pin unchanged
until a deliberate retirement or recreation plan is authorized.

### Flux Git sources

Keep the declared release tag and full immutable commit aligned. Verify that the
tag resolves to the proposed commit with the repository validator. Do not accept
a commit copied from a bot without independently resolving the tag.

### Helm and OCI sources

Update the source tag/digest or tag/commit pair and review the independently
rendered chart diff. When the renderer holds a separate chart-package checksum,
obtain the exact artifact, verify its digest, and update the checksum only after
reviewing why its bytes changed. Never remove the checksum gate.

### Bootstrap and downloaded tools

Version-only updates are intentionally insufficient. Update the verified
installer/release checksum, generated manifest checksum, and controller/image
digests required by the corresponding helper. Run its verify-only path where
provided. Do not use fresh-install helpers as an improvised K3s upgrade path;
the cluster manual must contain a rehearsed procedure first.

### Workflow actions

Pin `uses:` to a full action repository commit, retain minimal permissions and
hosted runners, and verify the advertised release tag against that commit. A
commented version is documentation; the commit is the security boundary.

### Repository-built images

Load [custom-image-builds](../custom-image-builds/SKILL.md). The image must be
built and pushed before a workload can be pinned to its resulting manifest
digest, but publication is a separate external side effect requiring authority.

## Validation and rollout

Run the complete current sequence in
[`.github/workflows/validate-cluster.yml`](../../.github/workflows/validate-cluster.yml),
including source and rendered Secret checks, catalog checks, strict schema
validation, root and Helm high-risk comparisons, Flux source-pin validation,
and independent Helm rendering. Do not substitute a narrowed unit test.

Review both desired-manifest and rendered-Helm diffs. A chart version bump can
change RBAC, host paths, security contexts, NetworkPolicies, CRDs, and defaults
without an obvious values-file change.

After an authorized merge, wait until Flux reports the exact merged Git
revision. Prove rollout, pod readiness, EndpointSlices, route conditions,
intended-network access, and service-specific behavior. For stateful changes,
confirm data integrity and a new completed backup. Retain the previous immutable
reference for rollback.

## Abort conditions

Do not merge or claim the update safe if:

- the proposed artifact cannot be tied to a primary upstream release;
- a tag, commit, digest, checksum, or coupled pin does not agree;
- a target architecture is missing;
- release notes identify an unplanned migration or irreversible schema change;
- a stateful backup/read-test is absent;
- rendered Helm or high-risk changes are unexplained;
- full validation fails or did not run;
- rollback would depend on a mutable tag or an image that may not read migrated
  data;
- a grouped PR combines risks that cannot be verified as one unit.

## Coverage limits and report

Renovate does not discover every raw Git revision, hardcoded artifact checksum,
controller digest, or cross-file coupling. A green Renovate PR is not exhaustive
supply-chain proof. CI records checksums, digests, SBOMs, and provenance where
configured, but does not generally verify signatures, admission attestations,
or vulnerability policy.

Report the dependency class, upstream evidence, old and new immutable references,
architecture proof, migration/backup impact, rendered diff, validation output,
rollback reference, live verification, and anything left unverified.
